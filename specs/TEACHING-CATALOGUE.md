## One continuous story

Use the same small assets through init, add, status/diff, commit, branch/worktree,
publish, merge, checkout/revert, history/restore, branch removal, ordinary eviction,
final retirement and metadata lifetime. Each lesson names its real Git command,
Tig intent/plan/observations, expected result, failure case and catalogue view.
Keep source acceptance distinct from storage convergence at every step.

The core sample has two works, one shared unchanged object, and old/new versions
of one replaced object. An active job preserves the old version across a release.
The external fixture profile maps working/history/backup to three fresh providers;
F/D/M can appear as teaching aliases, never required physical drive letters.
Use a second non-media interpretation of the same contract. All bytes are public,
small deterministic seeds; records and expanding operational state are distinct.
Portable provider directories model admitted synthetic failure domains. Their
real copy/hash/retention operations do not establish independent hardware custody;
every report and teaching view must retain that distinction. A production profile
still needs independently admitted actual volume/failure-domain evidence.

Every published lesson must be executable with checked expected results. A
target-only lesson is visibly unavailable until implemented and qualified; it
cannot appear to succeed through a simulated animation. Current source/provider
limitations remain stated. Use local temporary Git remotes and admitted fixture
providers for offline reproducibility. No download or third-party asset is needed.

## Visible evidence and counterexamples

The catalogue shows before/desired/planned/observed locations by exact object,
references and current protection, pending/held/completed state, copy/verify/
release order, unique versus copy bytes, estimated versus measured reclaim,
and why shared/job/unknown protection blocks a change. Use actual plans and
provider receipts. Stable object identity stays visible while locations change.

Required counterexamples: backup offline during merge, same-byte rename,
shared unchanged bytes, job-end demotion, new claim before removal, interruption
and exact retry, stale source/approval, same-hash reacquisition versus old retry,
and category/age selection with explicit final-loss consent. Age demonstrations
must identify any admitted fixture clock as simulated; no fabricated real age.
Metadata expiry must retain authority/replay fences and remain visibly pending
until its own implementation and validation exist.

being a demo. A fixture runner must bound effects to its freshly created roots
and explicitly admitted actions; keep private production access out of the UI.
